# Solana reserve governance prototype

This isolated Anchor 0.31.2 program is a **non-deployed, hard-gated custody prototype**, not a live or production-ready governance system. It contains the logic to hold the exact Token-2022 MSTRx mint in a PDA-owned vault, commit the vault balance at proposal creation, accept one signed snapshot vote per wallet, and allow the admin to withdraw only the uncommitted balance. It also contains code for `ACCUMULATE`, `LOCK_MSTRX`, Pump/PumpSwap CAPITAL buyback hold/burn/lock and a fixed Raydium marketing sale. The swap executors and their durable receipts passed a locked SBF build and 42 host tests on 25 September 2026, but **have not passed disposable mainnet canary tests**. `initialize` and `create_proposal` remain hard-disabled in this artifact. Do not route funds into it or describe the governance mechanism as live.

`initialize` is hard-disabled by the same release guard, so this build cannot accept governed funds even if someone supplies a matching program key. The buyback, marketing-sale and trader-funding paths have separate closed release flags. Before the disposable mainnet canary, review the exact test source and build a separate test artifact with every required action enabled; otherwise even initialization is impossible. Only the canary can establish live route behavior. Never treat these host tests or the test artifact as production sign-off.

The `declare_id!` value is a test-only placeholder derived from 32 bytes of `0x2a`; there is no deployable matching program keypair in this repository. Replace and review it before any deployment. No keypair is committed here.

## Custody and launch binding

- `initialize` requires the admin signer to be the program's verified loader-v3 upgrade authority. It creates the canonical Token-2022 MSTRx associated token account owned by the `[b"config"]` PDA. The reserve mint is hard-pinned to `XsP7xzNPvEHS1m6qfanPUGjNmdnmsLKEoNAnHjdxxyZ`, with 8 decimals; an arbitrary mint is rejected
- `initialize` runs before the CAPITAL mint is known: mint, token program, timestamp, slot and signature are empty. This lets the vault address be known before token creation. The same admin makes a single `bind_capital_mint` transaction after creation. The binding is one-time and immutable; a proposal cannot start before it
- The owner selected a non-upgradeable governance program after independent review. `create_proposal` additionally requires its own loader-v3 `ProgramData` account to have **no upgrade authority**. **Never revoke the upgrade authority of a binary with any required release gate still `false`**: an immutable false-gate program cannot be repaired under the same ID. First review and build the final binary with all required gates explicitly enabled, deploy/upgrade it and verify the actual program ID and deployed bytes. Only then revoke the upgrade authority and verify revocation; create the first binding proposal last. Revocation is not performed by this prototype. It cannot make MSTRx issuer-level controls immutable
- **The onchain bind instruction cannot verify a historical Pump creation event.** The protected offchain launch runner must independently verify the exact finalized mint-creation event on two RPCs, then submit mint, actual SPL/Token-2022 program, slot, signature and timestamp. A manual or malicious admin can bind another valid mint. This is a trust boundary, not an onchain proof of launch identity
- MSTRx has issuer-level Token-2022 controls including a transfer hook, permanent delegate, pause/default-account-state capabilities. The PDA does **not** override these mint-level powers. The present executor supports only a null active transfer-hook program and an unpaused mint, checking the raw extension layout at execution time; activation of the hook or pause blocks its checked transfers. Vault account state, issuer eligibility and real Token-2022 CPI behavior still require disposable mainnet canary tests. The code rejects transfer-fee and unknown dangerous extensions and verifies exact transfer deltas on supported routes, but this alone is not complete integration testing

## Proposal and reserve accounting

- One admin/proposer, one active proposal maximum. Proposal options are two to six unique fixed actions, always including `ACCUMULATE`; the `MARKETING_SALE` option pins one SOL recipient and allowed lock terms are constrained. Its Raydium CPI route is coded but hard-gated and unproven on SBF/chain, so this option cannot safely appear in a live ballot yet
- At proposal creation, the admin-provided starting amount must equal the **current vault token balance** and be greater than zero. The program commits that exact raw MSTRx amount; each spending option is frozen at 100% of it, while `ACCUMULATE` carries zero spend. New vault deposits after creation are free inventory, not part of the vote commitment
- The undeployed v3 account schema freezes a per-option `min_output_raw` before holders vote. Buybacks require positive raw CAPITAL units, marketing sale requires positive SOL lamports, and non-swap `ACCUMULATE`/`LOCK_MSTRX` require zero. The gated swap executors require the voted floor; marketing execution may raise but never lower it
- `withdraw_free(amount)` requires the admin signature and sends only to the canonical admin MSTRx ATA. It refuses to debit any committed amount: `free = vault_balance - committed`, checked without underflow. It uses a checked Token-2022 CPI with no extra hook accounts, rejects an active hook/paused mint, and checks the exact post-transfer vault balance
- Voting lasts one to twelve hours, requires a fixed 7% quorum, and has a five-minute result delay. One voter-signed vote-record PDA is allowed per proposal and wallet. A separate payer may cover rent/transaction fees
- No quorum or an exact top-weight tie releases the commitment and active pointer, leaving the reserve free. A winning `ACCUMULATE` is executed as a no-op by `finalize` after the five-minute delay: no token moves, the exact frozen amount becomes free, and its status is `EXECUTED`. Every spending winner **keeps both the full commitment and active pointer** so no second proposal can reserve the same inventory. Its status is `PASSED_NOT_EXECUTED` until its restricted action actually completes. There is no admin override or cancellation of that committed amount
- A passed `LOCK_MSTRX` may be executed by any payer after finalization. The exact frozen amount moves from the canonical reserve ATA into the canonical Token-2022 ATA of a `[b"reserve-lock", proposal]` PDA. Execution verifies an exact source debit and escrow credit before setting the proposal to `EXECUTED` (status 4) and clearing the active commitment. The selected lock term was frozen in the winning option before voting. The term starts at actual execution time
- The lock ATA can be pre-created or receive unsolicited MSTRx. Execution creates it idempotently, accounts for its prior balance, and moves **only** the proposal's frozen amount from reserve. A timed lock may be released by anyone after maturity, but only back into the canonical reserve ATA; any extra donations in the escrow transfer to reserve at the same time. A permanent lock has no release instruction. The lock record persists after release to prevent replay. This is a code-level guarantee only while the program is not changed by its upgrade authority and subject to MSTRx issuer controls
- The `ACCUMULATE` policy is an explicit owner decision. This host-tested transition does not prove onchain execution or justify lifting the release guard
- Once a finalized spending winner reaches its `executable_at` and remains unexecuted, the admin may open a fresh holder ballot over its same full commitment immediately. A failed replacement ballot can be replaced after its own result is finalized at its `executable_at`. Each replacement ballot starts at creation, lasts the selected one to twelve hours and is finalizable five minutes after closing; only initial ballots wait 24 hours to open. The old ballot is superseded, while committed MSTRx stays locked until holders choose `ACCUMULATE` or a spending action succeeds. No failed-transaction proof or admin unlock is involved

## Buyback implementation boundary

The selected buyback spends the **entire frozen amount in one transaction** or rolls back without changing the commitment. The undeployed onchain account schema is v3, with an immutable minimum output for each swap option. The exported but hard-gated `execute_buyback` pins the official 27-account Pump curve and 23-account PumpSwap exact-quote-in account maps, then checks reserve/trader/destination/supply conservation before writing a proposal-scoped durable receipt and clearing the commitment. Hold custody is permanent; timed CAPITAL locks release only into that custody. The separate admin SOL funding instruction remains hard-disabled. A configured admin can refund only uncommitted trader SOL above the System-account rent floor, and only while no proposal is active. Unrelated wallets may still send unsolicited SOL to the public trader PDA. Host tests do not establish a working buyback, Token-2022 mint/hook compatibility, CPI compute feasibility or onchain behavior. The release guard stays closed. See `docs/solana-governance-execution-plan.md`

The exported but independently hard-gated `execute_marketing_sale` route pins one Raydium CLMM pool, checks ordered tick arrays, sells the full frozen MSTRx input, unwraps actual WSOL, forwards the resulting SOL to the fixed recipient and writes a durable receipt before marking the vote executed. This is code-level behavior only. Live pool depth, compute limits, rollback and Token-2022 interoperability have not been proven on SBF/chain

Both swap executors create proposal-scoped, program-owned receipts in the **same successful transaction** as full-input execution and final destination checks. The buyback receipt binds proposal, winning action, venue, exact MSTRx spent, immutable minimum, actual CAPITAL acquired and custody/burn result. The marketing receipt binds the voted input/floor, execution floor and actual SOL forwarded. The site must not treat status `EXECUTED` as independently verified execution without the matching canonical receipt and live transaction confirmation. Neither route is deployed or canary-proven

## Snapshot proof and trust boundary

The proof hash protocol mirrors `services/solana/governanceSnapshot.ts`: SHA-256 with NUL-terminated leaf, node, root and network domains; little-endian u64/u128 integers; lexicographically sorted sibling hashes; odd-node carry; `root = sha256(ROOT_DOMAIN || leaf_count_u64 || total_weight_u128 || merkle_top)`. Rust unit tests include the matching TypeScript golden vector.

The admin still supplies the snapshot commitment and finalized source metadata. This program verifies votes **against that commitment**, not transfer-journal completeness, canonical RPC finality, exclusions accuracy, or the truth of holder balances. An independent, reproducible snapshot publisher and end-to-end proof tests remain required.

## Release blockers

1. SBF-build and review the coded Pump curve, PumpSwap and fixed Raydium executors, then enable the required gates in an isolated test artifact so the disposable canary can exercise them with real Token-2022 MSTRx. Prove exact full input, voted floors, destination/supply conservation, rollback, replay protection and the trader SOL refund in both Pump phases. Do not publish or promote the test artifact on host tests alone. The `LOCK_MSTRX` executor and `ACCUMULATE` transition also have **no onchain integration test or audit**
2. Verify the `ACCUMULATE` no-op and immutable-ProgramData constraint with the disposable canary, including a rejected upgradeable deployment and successful post-revocation finalization
3. Verify Token-2022 MSTRx transfer-hook and account-state behavior with cautious live reads and the disposable canary; the issuer's permanent delegate/pause powers remain external risks
4. Build and test the offchain finalized Pump event verification and one-time mint-binding runner. The owner keeps one powerful admin key, but the selected binding model requires permanent removal of the governance program's upgrade authority before the first proposal. An upgradeable deployment cannot pass the new `CreateProposal` account constraint
5. Replace the placeholder program ID, refresh production Anchor/Solana toolchain versions, obtain independent security review, generated IDL/client parity tests, and full disposable mainnet canary checks before any production fee routing. The owner declined a separate validator machine; this shifts runtime test cost and risk to the isolated mainnet canary, not to production funds
