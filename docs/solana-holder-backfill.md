# Solana CAPITAL holder-history coverage

The holder indexer scans every finalized produced block from the CAPITAL launch slot through its pinned target. It does this on the initial build and on **every incremental cursor advance**. It must read legacy, v0 and v1 transactions: a `getBlock` request capped at version 0 now fails for whole mainnet blocks containing v1 transactions, even when none of those transactions touch CAPITAL. Bitquery V2 `Solana(dataset: realtime).Transfers` can be useful for diagnostics, but is not the completeness authority for holder rewards. Bitquery documents roughly 12 hours of Solana V2 realtime `Transfers` retention and says out-of-window queries can silently return a truncated tail

Sources: [Solana transaction v1 integration](https://github.com/solana-foundation/solana-dev-skill/blob/main/skills/solana-dev/references/transactions-v1.md), [Bitquery coverage and retention](https://docs.bitquery.io/docs/graphql/data-coverage-retention/), [Bitquery realtime behavior](https://docs.bitquery.io/docs/graphql/dataset/realtime/)

Coverage of the realtime `Transfers` cube is **not** a proof that every
balance-changing CAPITAL instruction was returned. Bitquery documents burn
and supply changes in separate instruction/supply datasets rather than
explicitly guaranteeing that mint and burn appear in `Transfers`. A
previously indexed signature overlap cannot detect an event the vendor never
returned. Full-block discovery is therefore mandatory before publication,
including for an apparently healthy realtime window

Sources: [Bitquery Solana Transfers](https://docs.bitquery.io/docs/blockchain/Solana/solana-transfers/), [Bitquery Solana Instructions](https://docs.bitquery.io/docs/blockchain/Solana/solana-instructions/), [Bitquery Solana Token Supply Updates](https://docs.bitquery.io/docs/blockchain/Solana/token-supply-cube/)

## Finalized full-block path

The indexer pins the current target slot, block hash and block time. An untrusted or old-format cache triggers a rebuild from launch; a cache with valid full-block provenance extends from its prior finalized cursor with one overlapping slot. For each 32-slot chunk, it requires two independent RPC providers to agree on the produced-slot list, each complete block's hash and time, the full ordered transaction-signature list, transaction success flags and the set of transactions whose pre/post token balances or account keys mention the CAPITAL mint. Including static and loaded account keys covers a transient token account opened and closed inside one transaction. The candidate transactions are then re-read from both RPCs before the holder journal is accepted. Skipped slots are omitted only when both finalized `getBlocks` responses agree; a listed block that cannot be fetched is an error

Sources: [Solana getBlocks](https://solana.com/docs/rpc/http/getblocks), [Solana getBlock](https://solana.com/docs/rpc/http/getblock), [Solana transaction metadata](https://solana.com/docs/rpc/json-structures)

Progress is atomically checkpointed at `SOLANA_STATE_ROOT/recovery/capital-block-backfill.json` after each fully verified chunk. The target stays pinned across restarts. An incomplete run reports `HOLDER_INDEX_BACKFILL_IN_PROGRESS`, leaves the existing holder cursor and reward journal untouched, and publishes an unhealthy indexer heartbeat so reward planning does not advance from a stale snapshot. Version-1 checkpoints made before mint-key candidate detection are preserved under a `.superseded-*` name and rescanned, never reused. The durable holder cache carries versioned launch-to-target full-block coverage provenance and a SHA-256 digest over its canonical content, including every ordered token movement. Old vendor-only or pre-digest caches are rebuilt from launch; an altered digest stops reuse. This digest detects accidental corruption, **not** compromise by someone who controls the server and can recompute it. A complete run still must pass the journal's prior-transfer overlap checks and per-transaction two-RPC verification before the durable cursor is advanced. For new candidates, the verified full-block position and block hash are persisted through the checkpoint and checked against both parsed transaction reads, avoiding redundant accounts-mode block reads; older checkpoints without that proof retain the slower safe fallback. If the process crashes after completing a scan but before the journal write, it rescans rather than assuming coverage

`SOLANA_HOLDER_BACKFILL_SLOTS_PER_RUN` bounds work per indexer iteration to 1–2048 slots, default 2048. `SOLANA_HOLDER_BACKFILL_BLOCK_CONCURRENCY` permits 1–8 produced slots to be fetched at once, default 4 (two RPC requests per slot); completion remains atomic at each verified 32-slot chunk. The indexer sleeps 15 seconds between iterations by default (`SOLANA_HOLDER_INDEX_INTERVAL_MS`). Its previous 512-slot/5-minute schedule could not keep up with ordinary Solana slot production even with instantaneous RPC responses. These new defaults only remove that fixed mathematical backlog; they do **not** prove provider throughput or any service-level guarantee. The required RPC endpoints must serve historical finalized `getBlocks` and full `getBlock` data from launch. If either provider has pruned the interval, returns incomplete token metadata, disagrees with the other provider, or rate-limits before completion, coverage stays stopped. An initial build requires two full-block requests for each produced slot since launch, plus two parsed transaction reads for each CAPITAL candidate with persisted full-block proof; legacy proof-less checkpoints also require two accounts-mode block reads per candidate. Actual throughput and provider quota remain unverified. Do not delete or manually advance the checkpoint, reset the index cursor, or resume rewards using a present-day balance snapshot: a closing balance cannot reconstruct the holding-time path. Use two independent archival providers and let the same checkpoint resume

**Provider budget gate:** At Solana's current ~300 ms mainnet slot time, one complete block read per produced slot per provider alone approaches 288,000 block requests per day before skipped slots, extra cursor checks or CAPITAL candidate reads. The current polling path can make roughly 334,000 requests per provider per day if all slots are produced. At [Alchemy's published 40 CU per Solana `getBlock`](https://www.alchemy.com/docs/reference/compute-unit-costs), the full-block component alone is about 11.5 million CU/day; this can exceed a $100 monthly Alchemy cap. [Helius's free plan](https://www.helius.dev/pricing) lists 1 million credits/month and 10 requests/second, so it is not a credible sustained second full-history provider at this rate. These are estimates, not measured billing. Before sustained operation, benchmark actual produced slots, response sizes, credits/CU, rate limits and catch-up lag against both provider dashboards, then choose adequate paid archival capacity or a separately validated lower-cost completeness source. Never silently weaken the two-source check or continue payouts on an incomplete cursor

Bitquery V1 does expose historical Solana transfer rows, but verifying only those returned signatures against RPC cannot prove that *no* relevant transfer was omitted. V1 may be useful for diagnostics, not as the completeness proof for balance-time rewards. See [Bitquery historical Solana transfers](https://docs.bitquery.io/v1/docs/Examples/Solana/transfers)

On 24 September 2026, a read-only probe on the configured staging providers retrieved complete finalized blocks near the head and roughly 200,000 slots earlier with transaction version 1 enabled; the installed Solana SDK also decoded a real v1 transaction on each provider. On 25 September, the isolated `probe:solana-rpc` diagnostic additionally compared each provider's full and accounts-mode signature order at finalized slots `450127844` (1,328 transactions) and `449927944` (1,047 transactions); all four reads per slot agreed. These are point-in-time compatibility checks, **not** proof of sustained throughput, archival retention after a longer delay or correct CAPITAL accounting. During a disposable-token canary, rehearse an initial build, a gap greater than six hours, a provider outage, mismatched block lists and a process restart. Compare the rebuilt journal to an independently generated ledger and confirm that no payout is authorized while the scan heartbeat is unhealthy
